## 0. 决策摘要

| 项目      | 首版决策                                                                       |
| --------- | ------------------------------------------------------------------------------ |
| Demo 类型 | Windows 桌面浏览器可运行的第三人称 3D 叙事探索 Demo                            |
| 核心体验  | 玩家与星灵伙伴进入失去色彩的手绘本世界，行走与互动会让线稿环境持续恢复水彩颜色 |
| 技术栈    | TypeScript + Vite + Three.js + WebGL2/GLSL + 原生 HTML/CSS UI                  |
| 内容规模  | 1 张小地图、5～8 分钟流程、3 个故事节点、3 枚星屑、1 个跟随伙伴、1 个结局画面  |
| 美术方向  | 原创低多边形场景 + 铅笔线稿 + 水彩晕染；先用程序化占位资产，不等待外部模型     |
| 开发策略  | 先做“移动 + 染色”的可玩视觉切片，再补关卡、故事、伙伴和表现                    |
| 首版不做  | 战斗、完整奥拉星世界、账号、后端、多人、移动端适配、复杂物理、大规模开放世界   |
| 分发方式  | A0 先搭骨架和契约；A1～A5 按文件边界并行；A6 统一验收，集成者独占共享入口文件  |

一句话定义：**这不是“套水彩滤镜的走路 Demo”，而是“玩家亲手把一本黑白故事书走成彩色世界”的 Demo。**

## 1. 问题陈述

### 1.1 要解决的问题

用户看到参考项目后产生两个目标：

1. 复刻其可见核心效果：第三人称角色在水彩森林中行走，颜色从脚下漫开，溪水、花树和花瓣随探索恢复色彩。
2. 用更多故事填充世界，把童年 2D 游戏“奥拉星”所代表的伙伴、星屑、幻想地图和探索感，转化成可行走的 3D 空间。

当前缺少的不是完整游戏，而是一份能约束范围、统一技术接口、支持多 Agent 并行开发的首版需求基线。

### 1.2 首版真正需要验证的假设

- “线稿 → 水彩”的持续空间染色，是否能形成足够强的第一眼辨识度。
- 第三人称探索、伙伴跟随和短故事节点，是否能产生“童年 2D 幻想世界变成 3D”的感觉。
- 自定义材质、角色控制、关卡与叙事能否由多个 Agent 并行开发，并通过契约稳定集成。

### 1.3 产品价值

首版不是完整复刻，也不是技术演示拼图，而是一条从头到尾可完成的微缩体验。它应成为后续增加新地图、新伙伴、新故事和战斗系统的稳定底座。

### 1.4 使用方

| 使用方            | 主要目的                                         | 对应入口                       |
| ----------------- | ------------------------------------------------ | ------------------------------ |
| 体验玩家          | 在桌面浏览器中完成一段短时、可重置的水彩探索流程 | 正常游戏页面与 README 操作说明 |
| 外部开发者        | 学习或二次开发世界染色、第三人称控制和轻量叙事   | 开发指南、架构文档和源码       |
| 视觉/交互设计者   | 验证线稿与水彩、故事节点、镜头和 VFX 的组合      | PRD、架构流程与实际截图        |
| 多 Agent 项目团队 | 参考模块所有权、分支、PR、测试和集成方式         | 四 Agent 协作文档              |
| 维护者            | 控制范围、审查外部贡献、验证性能和发布版本       | 贡献指南、验收报告与发布清单   |

本项目首版不面向需要现成完整游戏系统、移动端直接游玩或稳定 SDK 接入的使用方。

## 2. 参考效果拆解

截图只能证明可见效果，不能证明原项目的确切实现。因此首版复刻的是**可见结果与体验**，不是臆测源代码。

| 参考中的可见特征               | Demo 中的转化                                                  | 优先级            |
| ------------------------------ | -------------------------------------------------------------- | ----------------- |
| 铅笔线稿森林与彩色森林同时存在 | 未探索区域为纸张底色、灰线和水溶性排线；已探索区域显示柔和水彩 | P0                |
| 角色往前走，颜色从脚下漫开     | 使用世界坐标染色遮罩，玩家经过后永久留下彩色路径               | P0                |
| 第三人称跟随镜头               | 角色位于画面中下部，镜头平滑跟随，可旋转和缩放                 | P0                |
| 蓝花、溪水、石头、花树依次变化 | 设计花地、溪流、花树三个故事节点                               | P0                |
| 花树由线稿变成粉色并掉落花瓣   | 最终节点进行大范围染色，并触发花瓣粒子                         | P0；精细粒子为 P1 |
| 柔和远山、草地与低饱和色彩     | 低多边形地形、雾化远山、实例化花草、柔光                       | P0                |
| 特定角色造型与原作资产         | 使用原创红斗篷旅行者和原创星灵占位形象                         | 非目标            |

### 2.1 核心效果的判定方式

必须同时满足以下四点才算复刻核心：

1. **空间性**：染色位置由世界坐标决定，不是固定在屏幕中央的圆形滤镜。
2. **持续性**：玩家离开后再回来，已恢复的颜色仍然存在。
3. **跨对象一致性**：地面、草、花、水和树读取同一张染色遮罩，不能各染各的。
4. **叙事性**：至少三个故事互动能主动触发大范围染色和环境状态变化。

## 3. 成功标准与反例标准

### 3.1 完整用户流程

1. 打开页面，看到一句简短引导并进入线稿森林。
2. 使用 WASD 移动、鼠标旋转镜头；脚下开始出现水彩颜色。
3. 跟随星灵与蓝色花丛，完成第一个故事节点，获得第一枚星屑。
4. 来到溪边，通过互动恢复溪水颜色，获得第二枚星屑。
5. 抵达花树根下，获得第三枚星屑并唤醒花树。
6. 花树变粉、花瓣落下、远景恢复色彩，镜头短暂拉远。
7. 出现结局文案和“重新进入绘本”按钮，可完整重置并再玩一次。

### 3.2 硬性验收标准

| 编号  | 验收项       | 通过条件                                                                                    |
| ----- | ------------ | ------------------------------------------------------------------------------------------- |
| AC-01 | 启动         | 在项目根目录执行 `npm install`、`npm run dev` 后可进入；`npm run build` 成功                |
| AC-02 | 移动与镜头   | WASD、鼠标旋转、滚轮缩放可用；角色不会穿出地图；镜头不会明显穿入地形                        |
| AC-03 | 脚下染色     | 移动 3 秒内能清楚看到线稿到水彩的变化，彩色路径与世界位置一致                               |
| AC-04 | 持续染色     | 离开区域再返回，颜色仍在；点击重新开始后才清零                                              |
| AC-05 | 跨材质一致   | 同一位置的地面、植被、水和花树使用相同世界遮罩，无明显错位                                  |
| AC-06 | 三个故事节点 | 花地、溪流、花树均可触发；有目标提示、互动提示、短对话与状态反馈                            |
| AC-07 | 伙伴与收集   | 星灵能跟随且不长期卡住；3 枚星屑均可收集，HUD 数量准确                                      |
| AC-08 | 结局与重置   | 花树唤醒后播放短结局；重置不会残留任务标记、星屑或染色                                      |
| AC-09 | 稳定性       | 连续游玩 10 分钟无崩溃、无未处理异常、无持续增长的明显资源泄漏                              |
| AC-10 | 性能         | 1920×1080、DPR 上限 1.5 的集成机实测：目标中位 55 FPS 以上，低帧不低于 30 FPS；记录测试设备 |
| AC-11 | 可调试性     | `?debug=1` 可查看 FPS、玩家坐标、当前任务和染色遮罩                                         |
| AC-12 | 数据解耦     | 故事文本、节点坐标和触发条件不写死在 UI 组件中                                              |

### 3.3 反例：出现以下任一情况即不通过

- 只是全屏黑白到彩色的后处理，角色实际走到哪里都不影响世界。
- 染色只作用于地面，树、草、水仍是普通材质。
- 玩家离开后颜色立即消失，无法留下探索路径。
- 故事只有长文本弹窗，环境没有对应变化。
- 有漂亮场景但没有开始、进程、结局和重置，无法完成闭环。
- 必须下载特定商业模型或原作资源才能运行。
- 首版加入战斗、背包、抽卡等系统，却尚未稳定完成染色与探索。

## 4. 范围

### 4.1 P0：首版必须完成

- 单场景第三人称探索，地图约 96m × 96m。
- 原创红斗篷旅行者，可使用简化模型；具备待机、移动和互动表现。
- 平滑跟随镜头、基础碰撞、地形高度适配。
- 世界坐标染色遮罩、脚下染色、故事节点大范围染色。
- 线稿与水彩两套视觉状态，覆盖地面、植被、水和花树。
- 花地、溪流、花树三个故事节点。
- 1 个原创星灵伙伴，具备跟随、互动和简单表情/弹跳反馈。
- 3 枚星屑收集，简洁 HUD、对话框、目标提示和结局页。
- 花树开花与花瓣粒子，完整重置功能。
- 调试面板、基础自动测试、构建与性能记录。

### 4.2 P1：P0 全部通过后追加

- 环境音、脚步、收集和开花音效。
- 更柔和的颜色扩散、水波、脚步涟漪与更多花瓣层次。
- localStorage 保存故事进度；首版默认刷新重新开始。
- 画质档位、音量设置、键位说明页、手柄支持。
- 更精细的原创角色模型与动画。

### 4.3 首版明确不做

| 不做项                               | 原因                                             |
| ------------------------------------ | ------------------------------------------------ |
| 战斗、技能、属性克制、宠物捕捉数值   | 会稀释染色核心，并引入大量平衡和动画工作         |
| 完整复刻奥拉星角色、地图、音乐或模型 | 首版验证的是 2D 幻想转 3D 的体验，不依赖原作资产 |
| 大型开放世界与多地图加载             | 当前只需证明一条 5～8 分钟的完整体验             |
| 后端、账号、联机、云存档             | 无助于核心视觉与叙事验证                         |
| 手机触控与全浏览器适配               | 先锁定桌面键鼠，避免输入和性能矩阵膨胀           |
| 完整刚体物理、复杂导航网格           | 平缓和风场景可用高度采样、圆形碰撞与跟随修正解决 |
| 写实 PBR、电影级景深与重度后期       | 与纸张水彩方向冲突，也增加 GPU 和调参负担        |
| WebGPU 作为唯一渲染路径              | 首版优先稳定落地，保留以后迁移的可能             |

## 5. 故事与关卡需求

### 5.1 故事梗概

一本星之绘本失去了颜色。旅行者“弥”与星灵“团仔”进入书页，发现只有真实的足迹和回忆能让世界重新显现。两人沿途找回三枚星屑，最终唤醒掌管这片花野的古树。古树开花时，玩家看到自己一路走出的彩色路径，理解“探索本身就是修复世界的方式”。

以上为首版可替换文本框架，重点是为环境变化提供因果，不追求复杂剧情。

### 5.2 角色

| 角色 | 功能                  | 首版表现                                              |
| ---- | --------------------- | ----------------------------------------------------- |
| 弥   | 玩家角色              | 红斗篷、白色内搭、简化低模；移动时斗篷轻摆            |
| 团仔 | 星灵伙伴与引导者      | 星形/团子形原创形象，悬浮跟随，在目标附近做出引导动作 |
| 花树 | 叙事主体而非 NPC 模型 | 线稿枯树 → 粉色花树 → 花瓣散落，承担结局反馈          |

### 5.3 地图与坐标基线

- Three.js 坐标：Y 向上，1 单位 = 1 米。
- 可玩范围：`X = -48～48`，`Z = -48～48`。
- 主路线沿负 Z 方向推进，Y 由地形高度函数计算。
- 所有 Agent 只能从这里读取关键位置，禁止在不同文件中复制另一套坐标。

| 地点       | 建议中心坐标 `(x, y, z)` | 触发范围 | 环境变化                               |
| ---------- | ------------------------ | -------- | -------------------------------------- |
| 出生草地   | `(0, terrainY, 32)`      | 自动     | 显示操作引导，脚下开始染色             |
| 蓝花坡     | `(-8, terrainY, 20)`     | 4m       | 蓝花显色，出现星屑 1                   |
| 溪流转折   | `(0, terrainY, 8)`       | 4m       | 溪水由灰线变蓝，出现星屑 2             |
| 花树根下   | `(0, terrainY, -22)`     | 5m       | 收集星屑 3，触发花树开花               |
| 结局瞭望点 | `(0, terrainY, -36)`     | 5m       | 可选步行收尾；结局也可在花树处直接触发 |

溪流可横跨 X 轴，位于 `Z = 8` 附近；设置 3～5 块踏石。首版溪水必须可通行或提供清晰绕行，不能因简化碰撞造成软锁。

### 5.4 三个故事节点

| 节点     | 前置条件        | 玩家动作               | 反馈                                           | 后续目标 |
| -------- | --------------- | ---------------------- | ---------------------------------------------- | -------- |
| `flower` | 无              | 靠近蓝花坡并按 E       | 4～6m 范围染色，团仔对话，星屑 1 可收集        | 指引溪流 |
| `stream` | 已完成 `flower` | 靠近溪边并按 E         | 水面恢复蓝色，出现短暂涟漪，星屑 2 可收集      | 指引花树 |
| `tree`   | 已完成 `stream` | 到树根互动并收集星屑 3 | 10～14m 范围扩散，树冠变粉，花瓣落下，远景染色 | 播放结局 |

对话每次最多 3 句，每句不超过 45 个汉字；允许点击/E 跳过。节点触发后必须幂等，重复按 E 不重复发星屑或重复推进任务。

### 5.5 体验节奏

- 前 30 秒：不用阅读长教程，直接理解“走动会留下颜色”。
- 中段 2～4 分钟：用蓝花和溪水展示不同材质的染色反馈。
- 最后 1～2 分钟：用花树、大范围色彩、伙伴反馈和短镜头形成情绪峰值。
- 结局画面让玩家看到自己走出的路径，避免立即用大面积 UI 遮住世界。

## 6. 技术栈分析与选择

### 6.1 方案比较

| 方案                         | 适合点                                                   | 首版代价                                                        | 结论                 |
| ---------------------------- | -------------------------------------------------------- | --------------------------------------------------------------- | -------------------- |
| Three.js + TypeScript + Vite | 与参考技术方向一致；浏览器即开即玩；便于拆模块和快速集成 | 角色控制、材质和关卡工具需自行搭建                              | **选用**             |
| React Three Fiber            | 声明式场景和 React UI 较方便                             | 增加 React/R3F 心智层；自定义 shader 与逐帧系统需要额外约束     | 首版不引入           |
| Unity + URP                  | 完整地形、动画、物理和编辑器能力强                       | Web 导出与多 Agent 文本集成更重；不能最直观地贴合 Three.js 参考 | 留作后续完整游戏选项 |
| Babylon.js                   | Web 3D 工程能力完整                                      | 团队当前参考与生态线索更偏 Three.js                             | 不重复评估           |

### 6.2 首版技术清单

| 层         | 选择                                     | 用途与约束                                    |
| ---------- | ---------------------------------------- | --------------------------------------------- |
| 语言       | TypeScript 严格模式                      | 所有跨模块数据有类型，禁止大量 `any`          |
| 构建       | Vite + npm                               | 快速开发、静态构建；提交 lockfile             |
| 3D         | Three.js，`WebGLRenderer` / WebGL2       | 首版固定该渲染路径，避免同时维护 WebGPU       |
| 材质       | GLSL + 集中式材质工厂                    | 地面、植被、水和树共享染色纹理与统一 uniforms |
| 后期       | `EffectComposer` + 自定义水彩 ShaderPass | 纸张颗粒、轻微边缘渗色；不做重度 Bloom        |
| UI         | 原生 HTML/CSS + TypeScript               | 首版没有复杂界面，不引入 React                |
| 角色与场景 | Three.js 几何体 + 可选 GLB/glTF          | 无资产也能运行；模型加载失败时有占位回退      |
| 数据       | JSON/TS 配置                             | 故事、节点、文本与场景对象解耦                |
| 音频       | 原生 Web Audio，P1                       | 不阻塞 P0；需用户首次交互后启动               |
| 测试       | Vitest + Playwright                      | 纯函数单测与浏览器 smoke test                 |
| 质量       | ESLint + Prettier + TypeScript 检查      | 统一代码风格，构建前必须无类型错误            |
| 协作       | Git，按 Agent 分分支或 worktree          | 每个里程碑提交，便于集成与回滚                |

### 6.3 关键取舍

- **[权衡] 选原生 Three.js，放弃 R3F 声明式便利**：少一层框架，但 UI 和生命周期需要手写；若后续 UI 大幅复杂化，可在不影响世界系统的情况下外层加 React。
- **[权衡] 选 WebGL2/GLSL，放弃首版 WebGPU/TSL**：兼容与调试更直接，但无法使用部分新计算能力；染色接口保持纹理输入，未来可换实现。
- **[权衡] 选 CanvasTexture 染色遮罩，放弃 GPU 流体扩散**：96m 小地图和 512² 遮罩足够，Agent 容易调试；代价是边缘精度和复杂扩散有限。当地图扩大或需要流体模拟时，替换为 ping-pong RenderTarget。
- **[权衡] 选程序化原创占位资产，放弃首版高精模型**：所有 Agent 可立即工作，但角色精细度有限；通过 GLB 加载接口保留替换点。
- **[权衡] 不引入物理引擎**：减少依赖和调参，但复杂坡面、推拉物和真实碰撞不在首版能力内；若后续加入战斗再评估 Rapier。

## 9. 核心系统开发需求

### 9.1 F-01 世界坐标染色遮罩

**首选实现：CPU 绘制 CanvasTexture，GPU 材质采样。**

1. 建立 512 × 512 的 RGBA 遮罩，R 通道表示永久显色程度；G 通道可用于短暂扩散脉冲。
2. 世界 XZ 映射到遮罩 UV；地图外区域按未显色处理。
3. 玩家初始位置执行一次 stamp；移动超过 0.25～0.35m 后再补笔刷，避免每帧无条件重绘。
4. 玩家基础笔刷半径建议 1.4～1.8m；故事节点为 4～14m。
5. 使用软边径向笔刷，并用小噪声扰动边缘，形成纸张吸色感，而不是完美圆形。
6. 遮罩更新上限 24～30Hz，只在脏标记存在时设置 `needsUpdate`。
7. 故事大范围扩散建议 0.8～1.5 秒完成，但最终结果写回永久遮罩。
8. 重置时清空遮罩、扩散动画和所有相关 uniforms。

**验收**：在世界中走“L”形路线，彩色路径也应是世界中的 L，而不是跟随屏幕或镜头旋转。

### 9.2 F-02 水彩与线稿材质

- 所有可染色材质读取同一 `ColorRevealMask.texture`、同一世界边界和噪声参数。
- 未显色：暖灰纸色、铅笔灰线、低饱和排线；不能只是简单降低饱和度。
- 已显色：柔和草绿、花蓝、溪蓝和树粉，保留纸张纹理与少量颜色不均。
- 使用世界坐标计算采样，避免模型缩放或相机移动导致纹理漂移。
- 优先通过统一的 `WatercolorMaterial` 工厂封装 `MeshStandardMaterial.onBeforeCompile` 或等价方案；锁定 Three.js 版本，shader 注入只允许出现在该模块。
- 首帧加载时预编译/预热关键材质，避免第一次染色明显卡顿。
- 全屏水彩 Pass 只作轻量统一质感，不得取代世界遮罩。

### 9.3 F-03 玩家与镜头

- WASD 相对镜头方向移动，角色朝移动方向平滑转向。
- 普通移动速度建议 3.5～4.5m/s；可提供 Shift 小跑，但不是必要系统。
- 鼠标拖动旋转，滚轮缩放；镜头有平滑阻尼。
- 角色贴地，使用地形高度采样；地图边界与大型树木使用简单圆形/胶囊碰撞。
- 摄像机做基础地形避让；树木遮挡淡化属于 P1。
- 对话期间可限制移动或降低速度，但必须保证关闭对话后输入恢复。
- 窗口失焦时清空按键状态，避免角色持续移动。

### 9.4 F-04 场景与地标

- 缓起伏地形、草地、蓝花、溪流、踏石、花树、远山构成一条清晰主路线。
- 草和花使用 `InstancedMesh`；远山使用低面数几何体，不加载大型外部场景。
- 花树必须在出生点无法直接看清最终彩色状态，保留前后反差。
- 已染色和未染色区域均要有足够辨识度，不能因全灰而看不到路线。
- 关键地标使用轮廓、伙伴引导和轻量目标文字，不依赖满屏箭头。

### 9.5 F-05 伙伴与星屑

- 团仔在玩家侧后方 1.5～2.5m 悬浮跟随，使用平滑追踪和上下浮动。
- 距玩家超过 12m 或卡住超过 2 秒时，可在不遮挡镜头的情况下回到玩家附近。
- 靠近当前故事目标时，伙伴给予朝向、弹跳或短对话引导。
- 星屑靠近即可收集，或统一按 E 收集；首版只能选择一种交互逻辑并保持一致。
- 星屑收集后立即更新 HUD，同一 ID 只能计数一次。

### 9.6 F-06 故事、UI 与结局

- HUD 仅保留当前目标、星屑 `0/3` 和必要操作提示。
- 对话框位于底部，不遮挡玩家与关键地标；支持 E/点击继续。
- 任务系统按 `flower → stream → tree → finished` 单向推进。
- 节点触发幂等；若玩家走回头路，不重复播放长对话。
- 花树开花后等待 2～3 秒再出现结局标题，让环境变化先被看见。
- 重新开始应恢复所有系统，不要求刷新网页。

### 9.7 F-07 VFX 与音频

- P0：花树花瓣、故事染色时的轻微粒子/涟漪。
- P1：脚步颜色涟漪、水面细波、风声、溪水、收集音和开花音。
- 粒子总量有上限，离屏或生命周期结束后及时回收。
- 音频必须在用户首次交互后播放，浏览器禁止自动播放时不能报错阻断游戏。

## 11. 非功能需求与测试

### 11.1 性能预算

- 染色遮罩首版 512²；未经性能评估不得直接升到 2048²。
- 渲染 DPR 上限 1.5；可添加低画质档位。
- 常态 Draw Calls 目标不超过 180，三角面目标不超过 350k。
- 首版本地资产总量目标不超过 30MB。
- 透明花瓣、草丛和水面的叠加面积必须受控。
- 页面隐藏时暂停非必要更新；所有 GPU 资源有 `dispose()` 路径。

### 11.2 浏览器与设备

- 首版支持当前稳定版 Chrome 和 Edge 的 Windows 桌面环境。
- 键盘与鼠标为唯一 P0 输入方式。
- 集成者需记录实测 CPU、GPU、内存、浏览器、分辨率、FPS 和资产体积；未记录设备的数据不算性能验收。

### 11.3 自动测试最低集

**Vitest：**

- 世界坐标到染色 UV 的映射，包括边界与越界。
- 故事前置条件、重复触发幂等和重置。
- 星屑去重与计数。
- 地形高度采样在地图边界内返回有限数值。

**Playwright smoke：**

- 页面加载无未处理异常，canvas 存在且尺寸非零。
- 键盘输入后玩家坐标变化。
- 调试模式可触发三个节点并到达结局。
- 点击重新开始后星屑为 0、任务回到起点、遮罩清空。

### 11.4 调试工具

`?debug=1` 开启：

- FPS、Draw Calls、三角面数。
- 玩家世界坐标和当前任务。
- 染色遮罩缩略图与笔刷半径。
- 节点触发范围、星屑位置和伙伴距离。
- 仅调试模式可用的节点跳转/触发按钮，便于自动测试。

## 15. 质疑与澄清

### 15.1 最弱假设：“想要复刻类似的效果”等于加一个水彩滤镜

我不同意这个理解。截图里真正有价值的是**世界因玩家行动而改变**。如果只做屏幕空间滤镜，即使画面相似，也失去探索留下痕迹的核心。首版必须先通过世界坐标、持续遮罩和跨材质一致性验收。

### 15.2 具体失败剧本：“想用更多的故事填充它”导致先写大量剧情

如果先扩展几十段对话、任务和角色，多个 Agent 会在染色接口尚未稳定时堆出大量耦合内容，最终得到“有文本的普通走路场景”。首版只允许三个节点；每个故事必须改变环境，不允许以文本量代替体验。

### 15.3 更简单替代：“把里面的 2D 世界搬来 3D”不等于先搬完整世界

把完整游戏地图、角色和系统都 3D 化不是首版的简单替代，而是范围失控。更简单且更能验证想法的方式，是保留“伙伴 + 收集 + 幻想地标 + 探索反馈”四种感受，只做一个花野场景。这个切片成立后，再决定地图和系统扩展。

### 15.4 该不该现在做

应该做，但应把首个交付定义为“可玩的视觉切片”，而不是“完整游戏的第一章”。只要 M1 的核心效果不成立，继续加故事、模型和音频都不会提高项目成立的概率。

### 16.1 Git 回滚策略

- M0～M4 各自提交并可打标签；并行 Agent 使用独立分支或 worktree。
- 每次集成只合并一个可说明的模块集合，合并后运行构建和 smoke test。
- 渲染故障可关闭后期 Pass，但**不得把世界染色本身作为可牺牲功能回滚掉**。
- 资产或 VFX 出问题时可关闭对应功能开关，故事闭环和移动必须保持可用。

## 17. 你可能没想到的关键点

1. **第一帧 shader 编译可能比平均帧率更破坏体验**：首次靠近花树才编译粉色材质会突然卡顿，关键变体需要预热。
2. **染色遮罩也是叙事状态的一部分**：结局应展示玩家路径；如果做存档，未来还需决定遮罩是否持久化，不能只存任务标记。
3. **“2D 变 3D”的童年感主要来自空间关系**：能绕过树、走到花丛背面、让伙伴跟随、从高处回望，比堆更多原作名词更重要。
4. **调试视图是多 Agent 项目的一部分，不是额外奢侈品**：没有遮罩、触发范围和坐标可视化，渲染与故事 Agent 会互相误判问题。
5. **故事完成事件与视觉扩散必须解耦但同步收尾**：逻辑不能等待粒子结束才完成，视觉也不能在逻辑重置后继续播放。
6. **重置功能能最早暴露资源泄漏和隐式全局状态**：首版就要求不刷新页面重玩，可提前发现单例监听、重复计数和纹理残留。

## 18. 最终 Definition of Done

只有全部满足以下条件，才称为“Demo 基础完成”：

- [ ] M0～M4 均有对应可运行版本，不只存在文档或静态截图。
- [ ] AC-01～AC-12 逐项有实测结果，反例标准均未触发。
- [ ] 世界染色、第三人称探索、三个故事节点、伙伴、星屑、花树结局构成完整闭环。
- [ ] 无外部资产时仍可用原创占位资产运行。
- [ ] 多 Agent 修改边界清晰，共享契约没有重复实现。
- [ ] 测试、构建、性能和修改文件清单已交付。
- [ ] 可在不刷新页面的情况下重新开始，并完成第二次流程。
- [ ] 后续扩展建议只建立在已运行版本上，不与 P0 缺陷混在一起。
